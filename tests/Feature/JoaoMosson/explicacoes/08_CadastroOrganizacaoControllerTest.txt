O QUE ESTE TESTE VERIFICA
------------------------------------------------------------------------------
* Testa se um cadastro com dados válidos grava a organização e o administrador (tipo administrador_organizacao), vinculados entre si.
* Testa se, depois do cadastro, o administrador fica logado e é redirecionado para o painel.
* Testa se, quando a criação do administrador falha, a organização NÃO fica gravada no banco (nem o usuário), e ninguém fica logado.

    CASO 2 (falha no meio do processo): se a criação do usuário der erro, a organização que JÁ tinha sido criada
    precisa ser desfeita. Isso se chama atomicidade: "ou grava tudo, ou não grava nada".

CÓDIGO:
            User::saving(function () {
                throw new \Exception('Erro simulado de banco na criação do integrante.');
            });
EXPLICAÇÃO:
    Força erro interceptando o momento da criação do usuário ou disparando exceção no evento
    
    O Eloquent dispara "eventos" nos models. "saving" é disparado ANTES de gravar (INSERT ou UPDATE).
    User::saving(função) registra um "ouvinte" que roda toda vez que um User está prestes a ser salvo.
    Este ouvinte sempre lança uma exceção, então qualquer tentativa de salvar um usuário falha.
    É uma forma de simular "o banco deu erro na hora de criar o administrador" sem precisar quebrar o banco.
    (O Laravel recria a aplicação a cada teste, então este ouvinte não vaza para os outros testes.)

------------------------------------------------------------------------------

                'administrador-email' => 'carlos@falhacorp.com',
                'administrador-cpf' => '52998224725',
                'password' => 'Segredo123#',
                'password_confirmation' => 'Segredo123#',
            ];
EXPLICAÇÃO:
    Dados 100% VÁLIDOS. Isso é proposital: a validação do formulário passa, a organização é criada
    e a falha só ocorre depois, na criação do usuário. É exatamente o cenário que queremos testar.
    (Com dados inválidos, o erro viria antes da transação e o teste não provaria nada sobre rollback.)

EXPLICAÇÃO:

------------------------------------------------------------------------------

CÓDIGO:
                $this->withoutExceptionHandling()->post(route('organizacao.criar'), $payload);
            } catch (\Exception $e) {
EXPLICAÇÃO:
    Normalmente o Laravel captura as exceções da requisição e as transforma numa resposta de erro
    (página 500). withoutExceptionHandling() desliga essa captura, para a exceção ORIGINAL chegar até o teste.
    
    O que acontece por dentro, passo a passo:
    a) a validação passa;
    b) DB::transaction abre a transação;
    c) Organizacao::create() faz o INSERT da organização (ainda provisório, dentro da transação);
    d) ao criar o usuário, o evento "saving" dispara e o ouvinte lança a exceção;
    e) o DB::transaction percebe a exceção, desfaz tudo (rollback, inclusive a organização) e relança;
    f) a exceção chega ao catch abaixo.

------------------------------------------------------------------------------

CÓDIGO:
                $this->assertEquals('Erro simulado de banco na criação do integrante.', $e->getMessage());
            }
EXPLICAÇÃO:
    Confere que a exceção capturada é a SIMULADA, e não outra (por exemplo, um erro de validação
    seria uma exceção diferente, com outra mensagem, e faria o teste falhar aqui).

------------------------------------------------------------------------------

CÓDIGO:
            $this->assertDatabaseMissing('organizacoes', ['cnpj' => '11444777000161']);
EXPLICAÇÃO:
    O ponto central do teste: a organização NÃO deve existir. Ela chegou a ser inserida no passo (c),
    mas o rollback do passo (e) a desfez. Se o controller não usasse transação, ela continuaria aqui
    e este assert falharia.
    (Se nenhuma exceção tivesse sido lançada, o usuário e a organização teriam sido gravados e os asserts
    desta parte falhariam, então o teste não passa "por acaso".)

------------------------------------------------------------------------------
